[TEST_PLAN](TEST_PLAN.md) owns strategy and scope;

## Catalog contract

This is the only manually maintained scenario registry. The initial catalog
maps all existing scenario tests and selected next exercises from the roadmap.
Broader roadmap topics have not all been decomposed into cases: percentages
apply only to included rows below, never to the entire application.

One row describes one concrete case at one test layer. UI and API checks of
related behavior may have different IDs. Existing overlapping tests remain
visible and are not evidence of additional business requirements. Technical
maintenance tasks are not scenario rows. Setup entries have no case ID.

- Add one static `case-id` annotation to each test declaration. Use
  `TC-AREA-001` identifiers, never recycle IDs, and keep them after renaming files.
- Parameterized data carries explicit IDs per case; array positions are not IDs.
- Included rows with no collected test are planned gaps, not validation errors.
- Excluded rows require a rationale. Do not silently remove gaps to improve a score.
- Edit scenario rows in this file, then run `npm run coverage:validate`. README links
  to this catalog; the generated report presents scenarios and execution evidence.
- Supported table cells are single-line text with `\|` for a literal pipe.
  The column names and start/end markers are part of the parser contract.

Risk is an initial qualitative estimate of what a regression would affect in
this learning application. It is separate from test execution priority:

- `critical`: unauthorized access or modification, or incorrect financial state;
- `high`: a core account, farm, marketplace, or ownership workflow breaks;
- `medium`: a limited workflow, validation, or data view becomes incorrect;
- `low`: an informational or auxiliary behavior changes.

Review these assignments when expected behavior becomes clearer. Excluded rows
retain a risk estimate, but remain outside coverage denominators.

## Mobile selection

Target browser emulation profiles are Pixel 5/Chromium and iPhone 13/WebKit.
TC-MOBILE-001 through TC-MOBILE-006 have test definitions. Generated execution
reports establish passing results for a given run. Project selection is defined
in playwright.config.ts; this section explains the intended scope.

Reuse the following existing test definitions and IDs in mobile projects:

| Existing ID    | Mobile risk and expected evidence                                                                                                                                                 | Existing source                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| TC-LOGIN-001   | Login controls remain usable and successful login shows the generated user's email on the profile.                                                                                | `tests/auth/login.noauth.spec.ts`        |
| TC-LOGIN-002   | Session survives reload, logout is reachable through the mobile header, and profile access redirects after logout. Inspect whether the shared logout action must expand the menu. | `tests/auth/login.noauth.spec.ts`        |
| TC-REG-001     | A user can complete registration on a small screen; response 201 and redirect to login remain required.                                                                           | `tests/auth/registration.noauth.spec.ts` |
| TC-REG-002     | Invalid email and short-password feedback remains visible on mobile and the user stays on registration.                                                                           | `tests/auth/registration.noauth.spec.ts` |
| TC-PROFILE-002 | Profile editing controls remain reachable and the changed name persists after reload with the email unchanged.                                                                    | `tests/auth/profile.isolated.spec.ts`    |

Keep one test definition per ID; device projects add executions of that definition,
not new business cases. Select these cases explicitly rather than including entire
authentication files. Current mobile projects collect `*.mobile.spec.ts`,
`login.noauth.spec.ts`, `registration.noauth.spec.ts`, `profile.isolated.spec.ts`
and `financial.isolated.spec.ts`,
filtered by /@mobile|@session/. The reuse rows above are selected, along with TC-FIN-001 and
TC-PROFILE-004/005/006 through their @mobile tags; other
registration cases and account deletion are outside this mobile selection.
Use independent generated users for each execution and retain existing assertions.

API boundary cases remain in API projects. Visual baselines,
physical-device keyboard behavior and broad device matrices are outside this
exercise. CI needs WebKit installation and system dependencies on both browser
cache hits and misses before the iPhone project can be verified there.

For TC-MOBILE-003, allow vertical scrolling and at most one CSS pixel of rounding
in horizontal geometry checks. Wait for the form before measuring; visibility
alone does not prove that a control fits within the viewport. This case does not
verify physical-device keyboard behavior or every responsive breakpoint.
